**DB schema (use this exact SQL so the code integrates well):**
```sql
-- APK RELEASE REGISTRY
create table if not exists apk_releases (
    id uuid primary key default gen_random_uuid(),
    version text not null,              -- e.g. "1.0.0" or "1.2.3-beta"
    file_id text not null,              -- Telegram file_id of the APK
    uploaded_at timestamptz default now(),
    changelog text,                     -- optional: notes for this release
    is_latest boolean default false     -- only one row should be true
);

-- TELEGRAM BOT SUBSCRIBERS
create table if not exists telegram_subscribers (
    chat_id bigint primary key,        -- Telegram chat_id (unique per user)
    username text,                     -- Optional: Telegram username
    first_name text,
    last_name text,
    subscribed_at timestamptz default now(),
    active boolean default true        -- in case they block the bot or opt-out
);

-- ENFORCE SINGLE LATEST RELEASE
create or replace function ensure_single_latest()
returns trigger as $$
begin
    if new.is_latest then
        update apk_releases set is_latest = false where id <> new.id;
    end if;
    return new;
end;
$$ language plpgsql;

create trigger trg_single_latest
before insert or update on apk_releases
for each row execute procedure ensure_single_latest();
````

**Functional requirements (exact behaviour):**

1. When *you* (the release uploader) send an APK file to the bot:

   * The bot must verify the uploader by parsing the APK filename `appName-password-versionName.apk`.

     * Parsing rule: split on `-` from the end: `versionName` = last part (strip `.apk`), `password` = second to last part, `appName` = everything before that (join with `-`).
     * Compare `password` (extracted) against allowed upload password(s) stored securely (e.g., `APK_UPLOAD_PASSWORD` env var or comma-separated `APK_UPLOAD_PASSWORDS`).
     * If password mismatch → reject and send a private message to uploader explaining failure. Do not proceed.
   * Capture `document.file_id`, version (from filename or caption), and `caption` (use as changelog). If caption is blank, store `"No changelog provided"`.
   * Insert a new row into `apk_releases` with `is_latest = true`. (DB trigger will clear other rows.)
   * Only after DB insertion succeeds, enqueue a Celery task to broadcast release notifications to subscribers.

2. Broadcast behaviour:

   * The broadcast message **must not** attach/send the APK file. Instead the message should contain:

     * Title: `New Watchers update: v{version}`
     * Short changelog (excerpt if long)
     * Instruction: `To download, open the bot and press /download`
   * Only subscribers that have ever clicked `/start` and have `active = true` in `telegram_subscribers` should be messaged.
   * Respect Telegram rate limits by default. Make the rate-limits configurable via env vars:

     * `MESSAGES_PER_SECOND` (default: conservative value, e.g., 20)
     * `BATCH_SIZE` (how many chat\_ids each Celery subtask handles — default e.g., 200)
     * Implement per-message delay `sleep(1 / MESSAGES_PER_SECOND)` or equivalent.
   * Implement robust error handling:

     * On `Forbidden`/`Bot blocked` errors, mark subscriber `active = false`.
     * On transient network/API errors, retry with exponential backoff (configurable max retries).
   * Support `dry_run` mode (env var `BROADCAST_DRY_RUN=true`) where messages are not actually sent — useful for testing.

3. `/download` command:

   * When any user runs `/download`, the bot fetches the row `apk_releases WHERE is_latest = true` and sends the APK using the stored `file_id` (via `bot.send_document(chat_id, file_id, caption=...)`) along with the version and changelog.
   * If no release exists → reply politely "No release available".

4. `/start` handler:

   * Capture `chat_id` and subscriber metadata (username, first\_name, last\_name) into `telegram_subscribers`. If already present, update `active = true`.
   * A friendly welcome message should be sent, explaining `/download` and that they can get release notifications.

5. Security & validation:

   * Validate uploaded file is `.apk` and mimetype/document size doesn't exceed acceptable limits (configurable).
   * Validate the filename parsing; if poorly formatted, ask uploader to follow `appName-password-versionName.apk`.
